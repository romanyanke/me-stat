# me-stat

Статика для [me.yanke.ru](https://me.yanke.ru): облако тегов и поиск по их пересечениям.
Собирается из Tumblr-блога `me-yanke`, деплоится на gh-pages.

## Как устроено

```
Tumblr API ──ttags──▶ tmp/source.json ──┬──▶ dist/tags.json ──index.js──▶ html/tags.js     (облако тегов)
                                        ├──build-search.mjs──────────────▶ html/search.html (поиск)
                                        └──build-combos.mjs──────────────▶ html/combos.html (комбинации)

Tumblr API ──build-thumbs.mjs──▶ tmp/thumbs.json ──▶ html/thumbs.js  (адреса превью)
```

- `tmp/source.json` — `{tags: {имя: id}, posts: {postId: [id тегов]}}`, полный слепок блога. Не в гите.
- `dist/tags.json` — теги с количествами (только те, что встречаются больше одного раза). Не в гите.
- `html/` — то, что уезжает на Pages. Тоже не в гите: собирается в Actions.

## Команды

### Обновить данные и облако тегов

```bash
npm start
```

Тянет все посты из Tumblr (`ttags`) и пересобирает `html/tags.js`. Нужен `TUMBLR_CONSUMER_KEY` в окружении.

### Обновить один пост

```bash
npm run post -- <post-id>
```

### Пересобрать только облако из уже скачанных данных

```bash
npm run html
```

### Собрать страницу поиска по тегам

С плиткой превью:

```bash
node build-search.mjs html/search.html --previews
```

Для Artifact на claude.ai — голый фрагмент, обёртку с charset и viewport он добавляет сам:

```bash
node build-search.mjs /путь/к/tag-search.html --previews --artifact
```

Без `--artifact` файл получает свои `<!doctype>` и `<meta viewport>` — иначе телефон рисует страницу в 980 px, а браузер уходит в quirks mode.

Обе собираются из `search-template.html`, весь индекс вшивается в страницу (~15 000 постов, ~6 200 тегов, 650–700 КБ). Сети странице не нужно, кроме превью и шрифтов.

#### Как устроены превью

Адреса картинок собираются заранее и лежат в `html/thumbs.js`:

```bash
TUMBLR_CONSUMER_KEY=$(op read "op://Personal/Tumblr/consumer key") node build-thumbs.mjs
```

API отдаёт по 20 постов за запрос, то есть весь блог — это около 750 запросов и пара минут. Собранное копится в `tmp/thumbs.json`, и повторный запуск обходит только новое: посты идут от новых к старым, и на первой полностью известной странице скрипт останавливается. `--all` обходит всё заново (например если Tumblr переедет на другой медиа-хост), `--out` меняет путь к файлу.

Из каждого поста берётся самый маленький вариант шириной от 500 px (~44 КБ): карточка ~250 px, 1280 px незачем. В файле хранится только хвост адреса после `https://64.media.tumblr.com/` — на 15 000 постов выходит около 1 МБ, по сети с gzip ~700 КБ. Страница грузит его **лениво**, при первом показе плитки, дальше он живёт в кеше браузера; сам поиск от этого не тяжелеет.

Раньше карточка забирала страницу поста и вынимала из неё `og:image`, но в сентябре 2026 Tumblr закрыл блог проверкой браузера: `me.yanke.ru/post/<id>` отдаёт 403 с телом «Checking your browser...» и без заголовка `Access-Control-Allow-Origin`, так что кросс-доменный `fetch` обречён. API на `api.tumblr.com` живёт отдельно и по-прежнему доступен, а ключ нужен только на сборке — в страницу он не попадает.

Если `thumbs.js` не подключился (нет рядом с файлом, пустой, или его режет CSP артефакта на claude.ai), страница гасит плитку и объясняет это плашкой; список работает как обычно.

Что умеет: пересечение любого числа тегов (И), исключение тега кликом по чипу, подсказки соседних тегов с числом постов внутри текущей выборки, запрос в адресе (`#Гамбург+небоскреб`, минус для исключения), сброс всех тегов одной кнопкой, плитка/список.

При каждой смене запроса страница отправляет родителю `postMessage({hash})` с таргет-origin `https://me.yanke.ru` — чтобы `/tagged` держал запрос в своём адресе. Вне этого origin (например в Artifact) браузер сообщение не доставляет и пишет предупреждение в консоль; на работу поиска это не влияет.

Страница живёт в айфрейме на [me.yanke.ru/tagged](https://me.yanke.ru/tagged), поэтому у неё нет своего заголовка и тема одна — тёмная, как на сайте: фон `#1c1c1c`, белый текст, жёлтый `#ffa` на наведении, Helvetica. Ниже 860 px колонки схлопываются, подсказки становятся горизонтальной лентой под поиском, ниже 560 px плитка идёт в два столбца.

### Собрать страницу интересных комбинаций

```bash
node build-combos.mjs
```

Пишет `html/combos.html` — пять списков по 200 строк, каждая ведёт в поиск на готовую выборку (`search.html#кот+капот`). Длину списков меняет `--limit`, путь задаётся первым аргументом.

Метрики и пороги — в `combos.mjs`. Считаются три величины:

- **постов** — сколько постов содержат все теги пары;
- **чаще случайного** (`lift = c·N / ca·cb`) — во сколько раз пара встречается чаще, чем если бы теги ставились независимо;
- **вложенность** — какую долю жизни тега занимает пара.

Сортировка по частоте бесполезна: наверху оказываются «Грузия + Тбилиси» и «Гоа + Индия 2», то есть одно место, названное дважды. Поэтому находки отбираются по высокому lift при условии, что редкий тег живёт не только в этой паре, и что не оба тега — имена собственные. Список «Похоже на один тег» устроен наоборот и годится как источник кандидатов для `retag.mjs`.

Топ-300 находок вшивается ещё и в `search.html` — на пустом экране поиска показывается дюжина сочетаний с кнопкой «другие». Ссылки с поиска на `combos.html` нет: страница комбинаций открывается сама по себе.

### Собрать всё сразу

```bash
npm run build
```

Это `html` → `search` → `combos` → `thumbs`. Цепочка строгая: упал шаг — дальше не идём. Данные при этом не обновляются, для свежих тегов нужен `npm start`.

## Сборка и публикация

Всё делает GitHub Actions — [.github/workflows/update.yml](.github/workflows/update.yml). Локально ничего собирать и коммитить не нужно: содержимое `html/` в гит не попадает, оно генерируется на стороне GitHub при каждом прогоне.

Раз в сутки в 23:00 UTC (02:00 по Москве) workflow берёт свежие теги через `ttags`, собирает все четыре файла и публикует папку `html` на Pages через `upload-pages-artifact` и `deploy-pages`. Адрес не меняется: `https://romanyanke.github.io/me-stat/`.

Запустить руками и посмотреть, как идёт:

```bash
gh workflow run update.yml && sleep 5 && gh run watch
```

Что нужно один раз на стороне GitHub:

- секрет `TUMBLR_CONSUMER_KEY` — `gh secret set TUMBLR_CONSUMER_KEY --repo romanyanke/me-stat`;
- источник Pages переключён на Actions — `gh api -X PUT repos/romanyanke/me-stat/pages -f build_type=workflow`.

#### Что кешируется между прогонами

Два кеша Actions, у каждого своя роль:

- `tmp/source.json` — кеш самого `ttags`. По нему библиотека считает, сколько постов доспросить: без кеша это 302 запроса каждую ночь, с ним — один. В первом прогоне в логе так и было: `Cached posts: 0. Requests to be sent: 302`.
- `tmp/thumbs.json` — собранные адреса превью, отсюда инкрементность `build-thumbs.mjs`.

Дельту `ttags` считает по **числу** постов (`totalPosts - cachedPostsCount`), а не по датам, поэтому переразметку старых постов и удаления он не видит. Из-за этого в ночь на воскресенье кеш тегов выбрасывается и блог обходится целиком; то же делает ручной запуск с галкой `full`:

```bash
gh workflow run update.yml -f full=true
```

У Tumblr лимит 1000 запросов в час на ключ. Обычная ночь — это один запрос `ttags` плюс пара на превью. Полный обход — 302 плюс не больше 300 на превью (`--max-requests`), то есть 602. Если кеш превью вытеснился (это происходит после недели простоя) и собирать надо с нуля, обход растянется на несколько ночей: там, где адрес ещё не собран, карточка честно покажет «нет превью».

Сам `ttags` — сторонний CLI без повторов, на пустом ответе Tumblr он падает с `Cannot read properties of null`, поэтому в workflow у него две попытки с паузой в пять минут.

Запланированные workflow у публичных репозиториев GitHub отключает после 60 дней без активности в репозитории; приходит письмо, включается кнопкой.

## Служебные скрипты

### Найти теги, которые ни к чему не привязаны

```bash
node cleanup-tags.mjs
```

Показывает список. Удалить их из `tmp/source.json`:

```bash
node cleanup-tags.mjs --apply
```

### Переименовать или снять тег на постах

```bash
node retag.mjs --remove <тег> --add <тег> <post-id> [post-id ...]
```

Сначала лучше вхолостую:

```bash
node retag.mjs --dry-run --remove палочка --add палочки 151794687275
```

Пишет в Tumblr, поэтому нужны все ключи: `TUMBLR_CONSUMER_KEY`, `TUMBLR_CONSUMER_SECRET`, `TUMBLR_TOKEN`, `TUMBLR_TOKEN_SECRET`, `TUMBLR_BLOG`.

Кандидаты на склейку (опечатки, единственное/множественное) копятся в `tmp/problematic-tags.md`.

## Теги по фото локальной моделью

У 4 596 постов из 15 082 стоит один-два тега — руками это не разобрать. `vision-tags.mjs`
показывает фотографию локальной vision-модели и предлагает, чем пост дополнить.

В Tumblr скрипт не пишет ничего: он складывает отчёт, а решение остаётся за человеком.
Одобренные теги применяются существующим `retag.mjs`.

### Что поставить

```bash
brew install ollama && brew services start ollama
```

```bash
ollama pull qwen2.5vl:7b && ollama pull gemma3:4b && ollama pull bge-m3
```

Около 10 ГБ. `qwen2.5vl:7b` — основная модель (видит объекты, отвечает по-русски),
`gemma3:4b` — быстрая для сравнения, `bge-m3` — эмбеддинги, чтобы подбирать кандидатов
из уже существующих тегов. Новых npm-зависимостей нет.

### Как запускать

```bash
node vision-tags.mjs 151136797725 151037839105
```

Без post-id берёт пять случайных недотегированных постов из `tmp/source.json`:

```bash
node vision-tags.mjs --limit 5
```

Сравнить две модели на одних и тех же постах:

```bash
node vision-tags.mjs --compare --limit 5
```

Флаги: `--model <имя>` (по умолчанию `qwen2.5vl:7b`), `--compare`, `--limit N`,
`--free-only` (только описание, без словаря — быстрее), `--size 640` (минимальная ширина фото).

Ключи лежат в 1Password, так что удобнее не экспортировать их в шелл, а подставлять
на один запуск — секрет не оседает в истории команд:

```bash
TUMBLR_CONSUMER_KEY=$(op read "op://Personal/Tumblr/consumer key") node vision-tags.mjs --limit 5
```

Без ключа скрипт тоже работает: он берёт фото со страницы поста через `og:image`
(так же, как превью в поиске), а текущие теги читает из `tmp/source.json`. Разница только
в свежести тегов — если пост переразмечали после последнего `npm start`, видно будет старое.

### Как устроено

```
post-id ──API──▶ фото (alt_sizes ≥640 px) ──▶ tmp/img-cache/<id>.jpg
                                               │
                                               ▼
                                    1. свободное описание
                                  VLM → {описание, объекты}
                                               │
                                               ▼
                                     2. привязка к словарю
                            bge-m3: слово → ближайший ваш тег (≥0.85)
                                               │
                                               ▼
                             tmp/vision-tags.json + таблица в консоль
```

Фото берётся из `photos[].alt_sizes` (или из `og:image`, если ключа нет) — самый маленький
вариант шириной от 640 px (~70 КБ):
1280 px модели не нужны, а 250 px уже не разглядеть. Скачанное лежит в `tmp/img-cache/`,
так что повторный прогон другой моделью в сеть не ходит. У постов с несколькими фото
берётся первое, остальные считаются и упоминаются в отчёте. Посты без фото пропускаются.

Запрос к модели идёт со структурированным выводом (`format` — JSON Schema), поэтому
ответ не приходится парсить из текста.

Свободные слова почти не совпадают с авторским словарём, поэтому есть второй заход:
все 6 232 имени тега один раз прогоняются через `bge-m3` и кешируются в
`tmp/tag-embeddings.bin` (~1–2 минуты разово), а дальше каждое названное моделью слово
тянется к ближайшему существующему тегу.

Показывать модели список кандидатов и просить выбрать — не работает: на шестидесяти
строках 7B то соглашается почти со всем, то возвращает пустоту, хотя нужный тег в списке
есть. Сравнение эмбеддингов стабильнее и не требует второго запроса к модели.
Порог — 0.85: точное попадание даёт от 0.85 и выше («деревянное» → `деревянный` 0.95),
ниже начинается снос смысла («мышь» → `миска` 0.80, «солома» → `соль` 0.71).
Когда слово и тег разошлись, в отчёте видно оба: `здание (здания, 0.86)`.

### Чего ждать

Словарь тегов авторский и далеко не только про «что на фото»: у поста `151037839105` теги
`август, календарь, ЦФТ, сися`. Модель не угадает «ЦФТ» и не поймёт шутку. Она годится
на предметный слой — `кот`, `еда`, `снег`, `небоскреб` — и на него же её стоит проверять.

На контрольных постах существующие теги воспроизводятся: `яйца`, `дрова`, `улитка`,
`ковер`, `парк` модель называет сама, и добавляет к ним то, что действительно на снимке —
`диван`, `храм`, `трава`, `горшок`. Промахи тоже есть и их видно сразу: выдуманные слова
(`несто`), лишние предметы, `в помещении` вместо `на улице`. Поэтому отчёт и читает человек.

Отдельная находка: `gemma3:4b` прочитала на фотографии календаря «августа 2013» —
то есть попала в авторский тег `август`, которого `qwen2.5vl:7b` не увидел. На текст
в кадре четвёрка иногда внимательнее.

Скорость на M1 Pro: `qwen2.5vl:7b` — 13–27 секунд на фото, в среднем около 17;
`gemma3:4b` — 6–7 секунд. То есть на 4 596 недотегированных постов уходит примерно
сутки на семёрке и около девяти часов на четвёрке. Пакетного прогона с чекпойнтами пока нет.

`--compare` держит модели снаружи цикла — сначала все посты одной, потом другой. Иначе
Ollama выгружает одну модель ради другой на каждом посте, и три секунды превращаются
в двадцать.
